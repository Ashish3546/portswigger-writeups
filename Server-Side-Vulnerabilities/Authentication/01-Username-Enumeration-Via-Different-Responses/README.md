# Lab: Username Enumeration via Different Responses

## Lab Description

This lab demonstrates a **username enumeration vulnerability** in a password-based authentication mechanism.

The application's login functionality responds differently depending on whether the supplied username exists. By analyzing these response differences, an attacker can identify valid usernames and subsequently perform a password brute-force attack against them.

---

## Objective

Identify a valid username by analyzing differences in the application's login responses, determine the corresponding password using the provided password wordlist, and successfully authenticate to the user's account.

---

## Vulnerability Type

- Username Enumeration via Different Responses
- Password Brute-Force

---

## Vulnerable Feature

Login authentication functionality.

---

## Entry Point

Login form (`POST /login`).

---

## Source

The attacker-controlled input originates from the login form:

```text
username
password
```

The username parameter is processed by the application's authentication mechanism and produces different responses depending on whether the account exists.

---

## Sink

The server-side authentication response generated by the `/login` endpoint.

The application unintentionally reveals information about username validity through differences in its HTTP responses.

---

## Root Cause

The application does not provide consistent responses for invalid usernames and valid usernames with incorrect passwords.

When a nonexistent username is supplied, the application returns:

```text
Invalid username
```

When a valid username is supplied with an incorrect password, the response changes to:

```text
Incorrect password
```

This behavioral difference allows an attacker to enumerate valid usernames.

---

## Data Flow

```text
Username / Password
        ↓
Login Form
        ↓
POST /login
        ↓
Authentication Logic
        ↓
Username Validation
        ↓
Authentication Response
        ↓
Response Analysis
        ↓
Valid Username
        ↓
Password Brute Force
        ↓
Successful Authentication
```

---

## Exploitation Process

1. Submitted an arbitrary username and password through the login form.
2. Intercepted the login request using Burp Suite.
3. Sent the request to **Burp Intruder**.
4. Selected the username parameter as the payload position using the **Sniper** attack type.
5. Loaded the username wordlist provided by PortSwigger.
6. Executed the Intruder attack.
7. Sorted the results by response length.
8. Observed that most username attempts produced responses of approximately the same length, while one response was different.
9. Investigated the anomalous response and compared it with a normal failed-login response.
10. Confirmed that the anomalous response indicated `Incorrect password` instead of `Invalid username`.
11. Identified the corresponding username as valid.
12. Changed the Intruder payload position from the username parameter to the password parameter.
13. Loaded the password wordlist provided by PortSwigger.
14. Executed the password attack against the identified username.
15. Analyzed the HTTP responses and identified the successful authentication attempt through its different HTTP status code.
16. Used the identified credentials to authenticate to the account and complete the lab.

---

## Payload

For username enumeration:

```http
username=§username§&password=invalid-password
```

After identifying the valid username:

```http
username=valid-username&password=§password§
```

The `§` characters represent the payload positions configured in Burp Intruder.

---

## Why the Attack Works

The application leaks information through differences in its authentication responses.

A nonexistent username produces:

```text
Invalid username
```

while a valid username with an incorrect password produces:

```text
Incorrect password
```

This allows an attacker to determine whether an account exists without knowing its password.

Burp Intruder automates this process by replacing the username parameter with values from the supplied username wordlist.

Once a valid username is identified, the same technique can be applied to the password parameter.

During the password attack, unsuccessful attempts returned:

```text
HTTP 200
```

while the successful authentication attempt returned:

```text
HTTP 302
```

The different status code indicated that the supplied credentials were accepted and the application redirected the authenticated user.

---

## Result

Successfully enumerated a valid username by analyzing differences in the application's authentication responses.

The corresponding password was then identified using Burp Intruder and the provided password wordlist.

The discovered credentials successfully authenticated to the user's account, completing the lab.

---

## Key Learning

This lab demonstrates how subtle differences in authentication responses can expose information about user accounts.

Important takeaways:

- Authentication responses should not reveal whether a username exists.
- Response length can be useful for identifying anomalous authentication responses.
- A response-length difference is an indicator that requires further investigation, not automatically proof of a vulnerability.
- Comparing an anomalous response with a normal response helps determine why the responses differ.
- HTTP status codes can reveal changes in authentication behavior.
- Burp Intruder can automate username enumeration and password brute-force attacks.
- Username enumeration can significantly reduce the search space for password attacks.
- Authentication error messages should be generic and consistent.
